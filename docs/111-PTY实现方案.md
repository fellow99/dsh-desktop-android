## 0. 摘要

本文在**已上架的 node-pty**（`io.github.fellow99:node-pty`，AAR 内 `libpty_node.so`）基础上，为
`dsh-desktop-android` 实现**完整 PTY 终端能力**，解禁上游 `terminal-controller` + `ui-sidebar-terminal`
两行，使右侧终端面板真正可用（不再"节点探针存在 ≠ 产品形态可用"）。

三件事打通：

1. **引擎/配套上架依赖直连**：以 `node-runtime:26.13.0` + `node-pty:26.13.0` AAR 替换手工投放 libnode.so
   v24.22.1 的旧链路（D1）。二者版本必须逐字一致（配对纪律，§3.2）。
2. **原生件加载垫片（S6）**：`libpty_node.so` 由 Kotlin `System.loadLibrary("pty_node")` 从
   `nativeLibraryDir` 预载（唯一可执行位，规避 Android 10+ W^X），Node 侧垫片让 `require('node-pty')`
   命中同一已加载 inode（D2，§5）。
3. **`@dsh-android/subprocess.spawnTerminal()` 落地**：实现上游 `SubprocessTerminalHandle` 契约的
   简化 Android 终端句柄，包 node-pty `IPty`（D3，§6）；随后解禁上游两行（D4，§7）。

## 1. 背景与现状

### 1.1 为什么现在是"已有基础"

上游 dsh 终端能力分两条路径，都经 `ctx.subprocess.spawnTerminal()` 汇聚：

| 路径 | 入口 | 现状（android） |
|---|---|---|
| **浏览器终端面板**（右侧栏，能力 #36） | `terminal-controller`（Host 端）→ `ui-sidebar-terminal`（Web 客户端 xterm.js） | both `disabled:true`（bundle）；Host 端 `spawnTerminal()` 抛 not-supported |
| **agent `terminal` 工具**（`terminal-bash`/`pwsh-terminal`，宿主给模型跑交互命令的后端） | `ctx.subprocess.spawnTerminal()` | 未启用；依赖同样的 spawnTerminal 契约 |

`dsh-desktop-android` 的 subprocess 提供方是 `@dsh-android/subprocess`（bundle `insert`），其
`spawnTerminal()` 当前**拍照式抛错**（`/dev/ptmx` 注释陈旧与探针矛盾）。因此：
- **唯一被卡住的点**就是 `spawnTerminal()` 没有原生后端；
- 上游 `terminal-controller` 已经类齐全：`resolveShell`、`discoverShells`、`BrowserTerminal`、
  `TerminalRetention`、Remote 流式 attach 都靠 `subprocess.spawnTerminal()` 的返回句柄驱动；
- **node-pty**（`forkpty`/`openpty` 的 N-API 原生件）已上架 Maven Central，恰好补上这唯一缺口。

### 1.2 现状证据（能力矩阵 #12 / #36 / T-003）

- `/dev/ptmx` chardev 节点在 run-as 探针下**存在**（2026-10 门禁记录），但此前 node-pty 无 android-arm64
  产物、本工程无 NDK 链 ⇒ 产品形态不可用（T-003 阻塞）。
- 现在 `libpty_node.so`（arm64-v8a）已上架；配对运行时与 N-API 均可解析 ⇒ **T-003 解锁路径成立**。

### 1.3 本文要回答的六个决策（头脑风暴共识）

| 决策 | 议题 | 结论（推荐） | 详见 |

| D2 | node-pty 原生件加载策略 | Kotlin `System.loadLibrary("pty_node")` 预载 + Node 侧 S6 垫片解析同一 inode | §5 |

## 2. 上架库与配对纪律（来自发布 runbook）

### 2.1 三个直连坐标

| Maven 坐标 | AAR 内容 | 版本 | 与 PTY 关系 |
|---|---|---|---|
| `io.github.fellow99:node-bridge` | Kotlin API + `libnode_bridge.so` + `libnode_host_client.so` + 引导 JS | **0.2.0** | JNI 桥；**与运行时无关**（dlopen 契约，换引擎不需重编）——**已在消费**，不动 |
| `io.github.fellow99:node-runtime` | `jni/arm64-v8a/libnode.so` + `libc++_shared.so` | **26.13.0** | 引擎；PTY 的 `DT_NEEDED libnode.so` / N-API（147）来源 |
| `io.github.fellow99:node-pty` | `jni/arm64-v8a/libpty_node.so`（**只有这一个 .so**） | **26.13.0** | PTY 原生件；`libnode.so`/`libc++` 靠消费方 runtime 提供，不带 |

### 2.2 配对纪律（必须逐字一致）

- `node-pty:<node>` 与 `node-runtime:<node>` **版本必须相同**（NODE_MODULE_VERSION 不同即不可用）。
- 只发布 **arm64-v8a** 一架构；x86_64 模拟器需 ARM 转译镜像。
- **发布顺序**（历史事实，本工程只消费不必再发）：runtime → pty → bridge。

### 2.3 版本选择说明（D1 决策）

> 你指定直连 `node-runtime:26.13.0` + `node-pty:26.13.0`。本文**采纳**，并明确其连锁影响：

| 维度 | 现状（24.22.1） | 目标（26.13.0） | 影响 |
|---|---|---|---|
| 引擎投放 | `provision-engine.mjs` 手工下 libnode.so 到 `src/main/jniLibs`（锁 sha256，不入库） | 消费 `node-runtime:26.13.0` AAR（`runtimeOnly`） | **移除手工 provision**，AAR 自动投放 |
| N-API / ABI | 137 | 147 | pty 必须 26.13.0 配对 |
| 小写国际 | small-icu | small-icu（26 发布线需确认同参数，见 §3.4 门禁） | 需复侧 G4 |
| 载荷 | 无 node-pty 原生 | 无（原生件走 AAR，不走载荷） | 载荷只加 node-pty JS |
| 回归风险 | — | 引擎大版本升级（24→26） | 用 D.3 核对单全量复侧 |

**备选（不采纳，记录在案）**：钉 `node-runtime:24.22.1` + `node-pty:24.22.1` 以最小改动解锁 PTY，避开引擎升级。
未采纳理由：与"直连最新上架库"意图不符，且 26 线已提供 B 面成熟 N-API。若后续 26 侧 G4 复侧失败，回退本备选作为 Plan B。

## 4. 架构与数据流

```
UI（WebView / 右侧终端面板，xterm.js）
   │  Remote 流（attach: TerminalInput↑ / TerminalFrame↓snapshot+output）
   ▼
terminal-controller（上游，Host 端）            ── bundle 解禁后启用
   │  agent.ctx.get('subprocess'/'workingDirectory'/'sandboxPolicy')
   ▼
@dsh-android/subprocess.spawnTerminal(spec)     ── 本方案新增（D3）
   │  构造 AndroidTerminalHandle（包 node-pty IPty）
   ▼
require('node-pty')  ── S6 垫片 ──► nativeLibraryDir/libpty_node.so（D2，Kotlin 已预载）
   ▲
libnode.so（26.13.0）解析 napi_* / DT_NEEDED（同 nativeLibraryDir）
   ▲
shell：/system/bin/sh -i（resolveShell ← subprocess.terminalEnvironment()=posix:/system/bin/sh）
```

数据流要点：

1. 模型/用户触发创建 → `terminal-controller.create` → `resolveShell` → `subprocess.spawnTerminal`。
2. `spawnTerminal` 经 S6 垫片 `require('node-pty')` → `spawn('/system/bin/sh', ['-i'], {cols,rows,cwd,env,
   name:'xterm-256color'})` 返回 `AndroidTerminalHandle`。
3. `BrowserTerminal` 监听 `handle.output`（PassThrough）推给 `Remote` 流；`write`/`resize` → `handle.write`
   /`handle.resize` → node-pty → PTY master。
4. 保留回收（`TerminalRetention`）依赖 `handle.inspectActivity()`；本方案保守返回 `unknown` ⇒ 不自动回收
   （安全默认，避免误杀活跃任务）。
5. `terminate()` / `close()` → node-pty `kill`/`resize` 群收 → 进程树清理。

## 5. 原生加载策略（D2 决策详解）

### 5.1 约束复核

- Android 10+ **W^X（A10）**：filesDir 载荷目录 `noexec`，`exec`/dlopen 应用私有目录 ELF 被拒。
- 系统安装的可执行位**唯一合规位置 = `nativeLibraryDir`**（AAR 投放、`useLegacyPackaging=false` 不压缩）。
- node-pty 的 `loadNativeModule()`（`lib/utils.js`）只在 `build/Release|Debug|prebuilds/<p><a>` 下找
  `pty.node`，绝不看 `nativeLibraryDir`；且载荷内放 `pty.node` 副本会因 noexec dlopen EACCES。
- ⇒ 结论：**不能在载荷内解析并 dlopen node-pty 原生件**；必须从 `nativeLibraryDir` 加载。

### 5.2 选定方案（两步）

1. **Kotlin 侧预载**（在 `DshRuntime` 启动 Node 前，或 NodeRuntime 初始化前）：

   ```kotlin
   System.loadLibrary("pty_node")   // 从 nativeLibraryDir 装载 libpty_node.so，reentrant、可执行
   ```

   这一步确保 inode 在进程内已载、N-API 模块表就绪（`NODE_API_MODULE(NODE_GYP_MODULE_NAME='pty_node', init)`）。

2. **Node 侧 S6 垫片**（`payload/shims/`，遵循 S1–S5 的"登记 + 唯一锚点 + 幂等"纪律），拦截
   `require('node-pty')` 的原生解析：把 node-pty 期望的 `build/Release/pty.node` 解析结果**指向
   `nativeLibraryDir/libpty_node.so` 的同一物理文件**，使 Node 的 `process.dlopen` 命中**已加载 inode**
   → 复用现有句柄、再派发 N-API init，不产生第二副本、不触 noexec。

   垫片机制（二选一，实施时以可验证者定）：
   - **A（symlink 桥）**：在载荷 `node_modules/node-pty/build/Release/pty.node` 放一个指向
     `nativeLibraryDir/libpty_node.so` 的**绝对 symlink**（symlink 无需 exec 位；target 可执行）。node-pty
     解析到该路径，`dlopen` 沿 symlink 命中 nativeLibraryDir 且与 Kotlin 预载同 inode ⇒ 复用。需验证 Node
     `require('.node')` 对 symlink + 非 noexec target 的行为。
   - **B（路径覆写）**：更稳——不依赖 relpath 约定，在 S6 垫片内给 node-pty 提供一小段解析宿主，用
     `process.dlopen(module, <nativeLibraryDir>/libpty_node.so)` 直接装载并返回其模块导出。实现无需改
     node-pty 源码，靠垫片重写 `Module._extensions['.node']` 的解析目标（仅当模块名为 `pty`）。

   推荐先试 **A**（改动最小、贴近上游约定）；若 A 在 noexec/转译下不稳定，切 **B**。无论 A/B，最终判据是
   设备端单一 PTY 能真实 fork `/system/bin/sh`（§8）。

### 5.3 失败上报（宪法 C2：不伪造）

原生件缺失、ABI 不符、SELinux 拒绝或加载失败时，`spawnTerminal()` **必须结构化上报**（复用现有
`SubprocessUnsupportedError` 家族，改为携带具体原因），**绝不**静默回退到假终端。`facts` 端点新增
`pty.loaded` / `pty.paired` / `pty.shell` 字段以暴露真实状态（debug-only）。

## 6. `spawnTerminal()` 实现（D3 决策详解）

### 6.1 契约（`@deepseek-ai/dsh-subprocess` 的 `SubprocessTerminalHandle`）

```
pid: number
output: Readable                       // PassThrough，终端输出按序送达，exit 后排空后 end
done: Promise<SubprocessOutcome>       // { exitCode, signal }
write(data: string): Promise<void>     // → PTY master
resize(cols, rows): Promise<void>      // → node-pty resize（改 winch）
inspectForeground(): Promise<...|undefined>   // 可选，确定前台进程组
inspectActivity(): Promise<{state:'busy'|'idle'|'unknown', revision}>  // 保留判定用
signalForeground(signal): Promise<number>     // 可选，进程组信号
terminate(): Promise<void>             // TERM→KILL 群收并等待 quiescence；原子幂等
```

### 6.2 实现位置与形态

- **文件**：`packages/subprocess-android/lib/terminal.js`（新增），导出 `AndroidTerminalHandle`；
  `lib/index.js` 的 `spawnTerminal()` 从抛错改为构造并返回。
- **形态**：**不移植**上游 `LocalTerminalHandle`（其依赖 linux-scope/containment/`ProcessInspector`/
  `BoundProcessOwner` 等桌面/Linux 专用机制，android 无 landlock、无隔离执行器）。写一个**最简闭合句柄**：
  - `output = new PassThrough()`；`terminal.onData` → `output.write`（背压 pause/resume 镜像上游语义）；
  - `terminal.onExit` → `output.end()` + resolve `outcome`（signal 名映射复用上游 `constants.signals` 表）；
  - `write/resize` 直接委托 node-pty；`terminate()` 按 `graceMs`（config 新增，默认 3000）TERM→KILL；
  - `inspectActivity()` **保守返回 `{state:'unknown'}`**（不触发保留自动回收，避免误杀）；
  - `inspectForeground()/signalForeground()`：可先返回 `undefined`/抛"unsupported"——`terminal-controller`
    仅在需要前台信号时调用；面板基础渲染不依赖。若后续需要 Ctrl-C/进程组信号，再在 publish 流程补
    PTY 前台进程组判定。
- **@dsh-android/subprocess 的 `terminalEnvironment()`** 已返回 `{platform:'posix', defaultShell:
  '/system/bin/sh'}`——`resolveShell` 即可解析；`resolveExecutable` 已放行 `/system/bin/*`。**零额外工作**。

### 6.3 配置

bundle row（shell-android 或 subprocess-android config）新增 `ptys:` 相关不做；仅 `terminal-controller`
默认 config 沿用（`disposeGraceMs` 等上游默认即可）。若需限流，可在 terminal-controller 行配置
`maxInputBytes/maxCols/maxRows`（上游已带默认）。

## 7. 解禁与载荷（D4 / D5 决策详解）

### 7.1 bundle `cordis.patch.yml` 变更

```yaml
- id: terminal-controller
  # disabled: true           ← 删除此行（解禁）
- id: ui-sidebar-terminal
  # disabled: true           ← 删除此行（解禁）
```

- 依赖锚定：`terminal-controller` 需 `subprocess`+`sandboxPolicy`+`workingDirectory`。android 已有
  `subprocess-android`、`sandbox-android`（策略层 `sandbox:'none'`）与上游 `working-directory` 行（未禁用）⇒
  三依赖齐备。**注意**：`terminal-controller` 的保持回收会读 `inspectActivity`，本方案 `unknown` 使保活不盲目回收。

### 7.2 载荷 node-pty JS（D5）

- node-pty（`1.2.0-beta.15`，subprocess-local 的硬依赖）经 `pnpm --filter @deepseek-ai/dsh deploy` 应已物化进
  载荷 `node_modules/.pnpm/` 并摊平到 `node_modules/node-pty`（assemble-payload 的 `materialize` 逻辑）。step
  **0 先核验**：
  ```bash
  node scripts/assemble-payload.mjs --deploy --apply
  ls build/payload-stage/root/node_modules/node-pty/lib/unixTerminal.js   # 必须存在
  ```
- 若未物化（上游 profile 或 deploy 过滤导致），在 assemble-payload 补拷贝规则：以 workspace 依赖身份
  vendor node-pty 的 JS 层（不含原生件）进 `node_modules/node-pty`。
- S6 垫片（§5.2）作为 `payload/shims/s6-node-pty.js` + `bootstrap.js` 登记行，遵循现有垫片纪律。
- 客户端侧：`ui-sidebar-terminal` 的 xterm.js 资产属标准 Web SPA，`webFrontend/dist` 已随包 ⇒ 解禁即渲染。

### 7.3 不触碰的边界

- `terminal-bash` / `pwsh-terminal`（agent `terminal` 工具）本方案**不默认启用**（其含 sandbox/Controlled
  Prompt 流水线，窗口另行评估）；本方案只解锁"右侧终端面板"。若需 agent 终端工具，在同一
  `spawnTerminal` 地基上再接（见 §9 后续项）。
- `ui-permission` / `permission` 仍禁用（无隔离执行器，C2），与 PTY 无关，不动。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 引擎 24→26 升级回归（ICU/ABI/JIT/持久化） | 面板可能带来副产品回归 | Plan B 备选（24.22.1 双件）；§3.4 门禁先行；D.3 全量复侧 |
| W^X / noexec：载荷内 `.node` 不能 dlopen | 原生件加载失败 | 走 nativeLibraryDir + Kotlin 预载（§5）；S6 A→B 双方案 |
| node-pty `loadNativeModule` 只认固定 relpath | 解析不到原生件 | symlink 桥（A）或 `_extensions['.node']` 覆写（B）；P1 判据锁死 |
| 转译环境（QEMU x86_64 + ARM 转译）下 PTY 不稳定 | 取证失真 | 真机优先；转译结果只作部分证据，登记 |
| SELinux 拒绝 `/system/bin/sh -i` 或 devpts | forkpty 失败 | 结构化上报（C2）；探针 + facts 暴露；仿 ark 真机 EACCES 修法 |
| 保留回收误杀活跃终端 | 任务中断 | `inspectActivity` 保守 `unknown`（不自动回收） |
| node-pty JS 未物化进载荷 | require 失败 | assemble-payload 补 vendor（§7.2） |
